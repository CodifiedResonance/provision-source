# Partial-batch recovery fix — 12 September 2026

The previous outbox trapped attention rows behind a generic reconciliation message without a server lookup. Publication was also coupled to an intermediate screen refresh. The revised flow persists the create acknowledgement into the draft before publication and refreshes only after the continuation attempt.

Uncertain saved/sending/attention operations call integrity_operation_v1 with the original operation ID, action and Source. A validated null data response means not committed and permits retry of the same immutable operation. A failed request (including 403/404), pending or failed server status never means absence. Committed metadata is followed by exact authorised replay because the pinned lookup deliberately omits the full result; this returns and adopts the original acknowledgement without another event. Operation IDs are never replaced by recovery.

Recovered create_lot data is persisted as draft.lotId and baseRevision before publish_v2. An already saved publication keeps its exact payload (including timestamp precision and note omission) on continuation. A draft clears only after an acknowledged publication, with a compare-and-swap check protecting newer tab edits. A later recovery also preserves a newer form rather than silently removing it. Original v1 saved operations are never relabelled v2.

Today, Saved work and the batch modal show **Batch created · publication not completed**, **Your draft is safe.**, and **Continue publication** for a created but unpublished batch. Saved work adds Check server acknowledgement for attention rows and shows when the same operation is safe to retry. Publication failures remain visible beside the action inside the open modal. Food, quantity, price, expiry, collection-window and note validation is checked before creating a lot; targeted errors appear beside their fields. Other modal errors appear beside the blocked action.
