# Partial-batch recovery fix — 12 September 2026

The previous outbox trapped attention rows behind a generic reconciliation message without a server lookup. Publication was also coupled to an intermediate screen refresh. The revised flow persists the create acknowledgement into the draft before publication and refreshes only after the continuation attempt.

Uncertain saved/sending/attention operations call integrity_operation_v1 with the original operation ID, action and Source. A validated null data response means not committed and permits retry of the same operation ID and original payload. A failed request (including 403/404), pending or failed server status never means absence. Committed metadata is followed by exact authorised replay because the pinned lookup deliberately omits the full result; this returns and adopts the original acknowledgement without another event. Operation IDs are never replaced by recovery.

Recovered create_lot data is persisted as draft.lotId and baseRevision before publish_v2. An uncertain or committed publication keeps its exact payload (including timestamp precision and note omission) on continuation. The verified rejection correction described below is the only amendment path. A draft clears only after an acknowledged publication, with a compare-and-swap check protecting newer tab edits. A later recovery also preserves a newer form rather than silently removing it. Original v1 saved operations are never relabelled v2.

Today, Saved work and the batch modal show **Batch created · publication not completed**, **Your draft is safe.**, and **Continue publication** for a created but unpublished batch. Saved work adds Check server acknowledgement for attention rows and shows when the same operation is safe to retry. Publication failures remain visible beside the action inside the open modal. Food, quantity, price, expiry, collection-window and note validation is checked before creating a lot; targeted errors appear beside their fields. Other modal errors appear beside the blocked action.

Regression evidence: eight new unit/integration-mock scenarios cover absent publish, lost create, lost publish, failed lookup, pending operation, account switch, newer draft retention and simultaneous continuation. The shared suite is 38 tests, not 76 independent scenarios across the two repos. A controlled browser fixture exercised the real draft/outbox/modal modules with IndexedDB and a simulated server: one existing batch, failed first publication attempt with a visible inline error, then one publication using one operation ID, followed by acknowledged draft removal and a simulated consumer potato offer. Missing expiry left zero batches and showed the error beside the field inside the modal. The internal HTTP fixture injects its own UUID/serial-lock support; hosted HTTPS uses native browser APIs. The fixture is development-only, explicitly enabled by a local .recovery-qa.local.json file, and is excluded from static deployment builds.

No protected approved-account runner was available in this task. The user's existing live staging draft, real backend event counts and real consumer offer still require the final authenticated retry; the simulated test is not described as live staging acceptance. Existing staging origins, return addresses, backend revision staging-20260910.1 and schema remain unchanged. No production or backend data/migration changes are made.
